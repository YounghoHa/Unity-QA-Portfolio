# QA Process

## 1. 테스트 기준

HEXIT에서는 테스트의 기준을 코드 정상 동작 여부, 기획 의도와 실제 플레이 결과의 일치 여부로 두었습니다.

### 기능 요구사항 검증

정의된 게임 규칙대로 기능이 동작하는지 확인합니다.

예시:
- AP가 부족하면 카드 사용 불가
- 영구 실드는 턴 종료 후 유지
- 과부하 수치는 지정 값만큼 증가
- 덱 최대 수량은 8장

### 사용자 시나리오 검증

실제 플레이 흐름을 기준으로 시스템 간 연결을 확인합니다.

예시:

맵 선택 → 전투 → 보상 → 상점 → 덱 반영 → 다음 스테이지

개별 기능이 정상이어도 이 흐름에서 데이터 전달이나 상태 유지가 깨지면 FAIL로 판단합니다.

### 예외 / 경계값 검증

기획된 한계값 또는 비정상 입력 상황에서 예상하지 못한 결과가 발생하지 않는지 확인합니다.

예시:
- AP = 0
- 덱 8장 상태에서 상점 카드 구매
- 덱 전량 소진
- 실드 상태에서 턴 종료
- 카드 애니메이션 도중 추가 입력

### 기획 / UX 검증

기능이 정상적으로 동작하더라도 실제 플레이 경험이 게임의 목적과 다르면 개선 대상으로 판단합니다.

대표 사례:
- 미래 노드를 ? 로 가렸지만 스크롤을 통해 전체 맵 구조를 확인할 수 있었던 문제
- 서로 다른 카드 조합 규칙이 정상 동작해도 조합식을 외워야 하는 부담이 커졌던 문제

---

## 2. QA 진행 흐름

1. 기획 의도 확인
2. 기대 결과 정의
3. 테스트 조건 및 시나리오 설정
4. 실제 플레이 테스트
5. 기대 결과와 실제 결과 비교
6. 문제 재현
7. 발생 조건 축소
8. 우선순위 / 영향도 판단
9. 기획자 및 개발자와 수정 방향 협의
10. 수정 후 동일 조건 재테스트
11. 연관 기능 회귀 테스트

---

## 3. 문제 분석 방식

전체 전투가 이상하다고 판단하는 대신 가능한 경우 기능을 단계별로 분리하여 확인했습니다.

예시: Monster Intent

MonsterData  
→ MonsterActionData  
→ 행동 선택  
→ Intent 표시  
→ Animation  
→ EffectOption 적용

각 단계를 나누어 검증하여 어느 지점에서 실제 결과가 기획 데이터와 달라지는지 확인했습니다.

---

## 4. 협업 방식

문제를 발견했을 때 단순히 "이상하다"라고 전달하지 않고 다음 내용을 정리하여 공유했습니다.

- 현재 문제
- 재현 조건
- 기대 결과
- 실제 결과
- 현재 구조에서 가능한 수정 방법
- 변경안의 장점 / 단점
- 기획 목적에 미치는 영향

기획자와 논의할 때 구현 가능성과 플레이 경험을 함께 비교하여 변경 방향을 결정했습니다.

---

## 5. 회귀 테스트

문제가 수정된 기능만 다시 확인하지 않고 연관 기능도 함께 검증했습니다.

예시:

Intent 문제 수정  
→ 동일 행동 확인  
→ 다른 행동 확인  
→ 애니메이션 확인  
→ 실제 효과 확인

이를 통해 수정으로 인해 다른 행동이나 시스템에 새로운 문제가 발생하지 않았는지 확인했습니다.

---

## 6. 테스트 효율화

특정 전투 상황을 만들기 위해 매번 전투를 처음부터 반복하는 비용을 줄이기 위해 BattleTestButton을 제작했습니다.

테스트 버튼으로 다음 조건을 즉시 생성할 수 있습니다.

- 플레이어 체력 회복
- 공격력 버프
- 버프 지속 턴 설정

이를 통해 같은 조건을 빠르게 반복 생성하여 재현 테스트와 회귀 테스트 시간을 줄였습니다.
